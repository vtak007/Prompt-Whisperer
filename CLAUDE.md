# CLAUDE.md

Guidance for working in the Prompt Whisperer Chrome extension repo (formerly "Prompt Assistant"). See the user's global `~/.claude/CLAUDE.md` for cross-project conventions (branching, doc-update gating, `.ini` handling, etc.) — not duplicated here.

## Key Files

| File | Description |
|---|---|
| `manifest.json` | MV3 manifest: permissions, side panel config, background service worker registration. |
| `background/service-worker.js` | Sets side-panel-on-icon-click behavior; seeds storage on first install. |
| `sidepanel.html` / `sidepanel.css` / `sidepanel.js` | The side panel shell, design tokens/theme, and the app's entry point (render loop + all event delegation). |
| `store/store.js` | In-memory state container (`getState`/`setState`/`setStateSilent`/`subscribe`). |
| `store/actions.js` | All state mutations + persistence calls live here; views never touch storage directly. |
| `router/router.js` | Hash-based view router (`#/library`, `#/create`, `#/edit/:id`, etc.). |
| `services/storage.js` | `chrome.storage.local` wrapper; owns the `{schemaVersion, categories, prompts, settings}` root shape and the migration stub. |
| `services/promptInsertion.js` | Injects `insertTextIntoActiveElement` into the active tab via `chrome.scripting.executeScript` to insert prompt text into a focused field. |
| `services/optimizer.js` | `optimizePrompt()` provider abstraction; backed by a deterministic mock provider (default) and a live `anthropicProvider` that calls `/v1/messages` directly from the browser. |
| `services/importExport.js` | JSON export builder + import validation/preview/duplicate-detection. |
| `services/search.js` | Combined keyword/category/tag prompt filtering. |
| `services/clipboard.js` | Copy-to-clipboard with a `document.execCommand` fallback. |
| `views/*.js` | One render function per screen (Library, Create, Edit, Optimize, Import/Export, Search, Settings). Pure functions of state → HTML string. |
| `components/*.js` | Shared render fragments (Header, Navigation, PromptCard, TagChip, Modal, Toast, Footer). |
| `components/icons.js` | The inline-SVG icon set. `icon(name)` returns an SVG string; all strokes/fills use `currentColor` so icons recolor from CSS. |
| `store/privacy-policy.html` | Standalone privacy policy page for the Chrome Web Store listing; not loaded by the extension itself. |
| `data/seed-data.js` | The 5 sample prompts + starter categories used on first install. |
| `utils/*.js` | `ids.js` (uuid/slug), `dates.js`, `validation.js`, `dom.js` (escaping, delegation, debounce). |

## Architecture notes

- **No framework, no build step.** Every view/component is a plain function returning an HTML string; `sidepanel.js` re-renders the active view's container on every store change via `innerHTML`.
- **Uncontrolled text fields.** Title/Content/Notes/Optimize textareas are *not* synced to the store on every keystroke (that would blow away cursor position on re-render). They're read from the DOM at the moment of an action (tag add/remove, submit, run-optimize). Only the Search keyword field re-renders live (debounced), using a focus-preservation helper in `sidepanel.js` (`renderPreservingFocus`) to keep the caret in place.
- **`setStateSilent` vs `setState`**: `setState` triggers a full re-render of the view region; `setStateSilent` updates state without notifying subscribers — used for cheap per-keystroke flags like `formDirty`.
- **Insertion permission model**: the manifest declares `host_permissions` for `http://*/*` and `https://*/*` (not just `activeTab`) because clicking a button *inside* the side panel does not count as one of the gesture types that grants `activeTab`'s temporary host access (only toolbar-icon clicks, keyboard commands, and context-menu items do). `chrome://` pages remain unreachable by design — Chrome blocks script injection there for every extension. The same `host_permissions` also cover the Anthropic API fetch, so no separate manifest change was needed to add the live optimizer.
- **Live optimizer provider**: `services/optimizer.js`'s `anthropicProvider` calls `https://api.anthropic.com/v1/messages` directly from the side panel with the `anthropic-dangerous-direct-browser-access: true` header — this is Anthropic's documented, supported mechanism for browser-origin calls, not a workaround. The user's API key is read from `state.settings.optimization.apiKey` (stored in `chrome.storage.local`, plain text) and threaded through `optimizePrompt()`; it is never logged. Anthropic's dedicated `/v1/experimental/improve_prompt` "Prompt Improver" endpoint was considered and rejected — it's an experimental Workbench-only tool being retired August 17, 2026, so the live provider instead sends a custom rewrite instruction to the standard, stable Messages API.
- **Model list**: `services/optimizer.js`'s `fetchAnthropicModels(apiKey)` calls `GET /v1/models` and caches the result in `state.settings.optimization.{availableModels, modelsFetchedAt}` via the "⟳" button in `views/SettingsView.js` (`refresh-models` action in `sidepanel.js`). The Model field is a plain text `<input>` with a `<datalist>` populated from that cache — a real dropdown UX while still allowing any manually-typed model ID, and gracefully degrading to a blank list before the user has ever fetched (no API key required to type a model manually, only to fetch the live list).
- **Autofill gotcha**: a plain text field placed directly before a `type="password"` field gets pattern-matched by Chrome as a username/password login form and autofilled accordingly (this bit the Model field in Settings, next to the API Key field). Give such fields explicit `autocomplete="off"` (plain fields) / `autocomplete="new-password"` (secret fields) to opt out.
- **Brushed-chrome theme**: the whole metal look in `sidepanel.css` is CSS-only — layered `linear-gradient`s for the steel sheen, `radial-gradient`s for the corner rivets, and `inset` box-shadows for bevels. No image assets. Only the **light** palette is authored; `:root[data-theme='dark'] #app` re-renders it with `filter: invert(1) hue-rotate(180deg) brightness(.78) contrast(1.06)` — the `hue-rotate` is what keeps cyan reading as cyan after the invert rather than flipping to red. Consequence: any new colour only needs defining once, but it also means *every* dark-mode colour is derived, so a change that looks right in light can go muddy in dark — check both. `settings.appearance` defaults to `'light'` (in `data/seed-data.js` and as the fallback in `sidepanel.js`'s `render()`), since light is the palette the theme was designed against.
- **Text on the steel gradient**: the `#app` gradient's mid band is `#66757e`, light enough that even pure black text only reaches ~4.4:1 contrast there, and mid-grey (`#48545b`, the original `--muted`) manages just ~1.6:1 — effectively invisible. Anything rendered directly on the panel background (not inside an input/card) therefore needs both a dark colour **and** a `text-shadow` halo to separate it: light halo behind dark text (`label`, `.hint` use `--muted` `#16222a` with a white halo), dark halo behind light or cyan text. Don't add plain grey secondary text to the panel background without checking it against that mid band.
- **Icons are inline SVG, coloured by CSS**: `components/icons.js` exports `icon(name)`; every path uses `stroke="currentColor"`/`fill="currentColor"`, so colour comes from the surrounding rule (e.g. `.list-item-label.is-accent svg { color: var(--accent) }`) rather than being baked into the markup. Add new icons there rather than inlining SVG in a view.
- **Don't hide working controls with CSS.** A previous styling pass added `display:none` rules that silently removed reachable functionality — the footer Help button (`#app-footer .icon-btn`) and the category/tag rename+delete buttons (`.list-item > span:last-child .icon-btn`) — while their handlers in `sidepanel.js` stayed live and correct. The same pass truncated prompt tags to two with `.slice(0, 2)` in `PromptCard.js`, silently dropping data from the display. When restyling, check that every `data-action` still has a visible, clickable target; the handler existing is not evidence the control is usable.
- **Library sidebar sections**: Categories, Tags, and Favorites are each independently collapsible (`state.categoriesExpanded` / `tagsExpanded` / `favoritesExpanded` in `store/store.js`, toggled via `toggle-categories`/`toggle-tags`/`toggle-favorites` actions in `sidepanel.js`) — transient UI flags, not persisted to `chrome.storage.local`, so they reset to collapsed on every side-panel open. All three lists are re-sorted alphabetically on every render (categories/tags by name, favorites by prompt title) rather than sorted once and stored, so newly added/renamed entries always land in the right place with no extra bookkeeping. Favorites renders the actual favorited prompts nested under the header (title only, `open-prompt` action) rather than a category-style count row. `state.libraryFilter` defaults to `{ type: 'none' }` (see `store/store.js`) so the prompt list starts blank with a hint until the user explicitly picks "All Prompts", a category, or a tag — `'favorites'` was removed as a filter type since Favorites no longer has a summary row that sets it. `filterPrompts()` in `views/LibraryView.js` also sorts the resulting prompt cards alphabetically by title. Collapsing Categories or Tags (`toggleCategoriesExpanded`/`toggleTagsExpanded` in `store/actions.js`) resets `libraryFilter` back to `'none'` if the active filter belonged to that section, so the prompt list goes blank again instead of staying populated underneath a collapsed section.
- **View scroll reset**: `render()` in `sidepanel.js` tracks `lastRenderedView` and resets `#app-view`'s `scrollTop` to 0 only when `state.currentView` actually changes (not on every render) — this fires on the `hashchange`-driven re-render after a view switch (e.g. saving a prompt navigates back to Library, or clicking Create/nav tabs), while normal in-view scrolling (e.g. scrolling a long Library list) is left untouched since `currentView` hasn't changed.
- **Tags have no id/storage record** — unlike categories, a tag is just a string embedded in each prompt's `tags` array (derived/counted on the fly in `views/LibraryView.js`'s `computeTagCounts`). Rename/delete (mirroring the category ✎/🗑 pattern in the Library sidebar) is implemented as a bulk find-and-replace across `prompts` in `services/storage.js` (`renameTag`/`deleteTag`) rather than a lookup-and-patch on a separate collection.
- **Search view dropdowns are sorted ascending**: `renderSearchView` in `views/SearchView.js` sorts `categories` by `name` (via `localeCompare`) before building the "Filter by Category" `<option>` list; `uniqueTags()` in the same file already sorted tags via `Array.sort()`. Both dropdowns are rebuilt fresh on every render (not cached/stored sorted), matching the same re-sort-on-render pattern used by the Library sidebar.
- **Create/Edit Tags field is a dropdown + "+ New Tag" button**, matching the existing Category field's dropdown + "+ New Category" pattern exactly (`views/CreateView.js`, reused by Edit since both call `renderPromptForm`). Picking an existing tag from the `<select data-field="tag-select">` adds it as a chip immediately (`change` listener in `sidepanel.js`) and resets the dropdown to its placeholder. "+ New Tag" opens a `new-tag` modal (`components/Modal.js`, mirroring `new-category`'s shape) whose submit handler validates via the existing `validateTagName` and adds straight into `draft.tags` — no `createTag`/storage call, since (per the tag-storage note above) a tag isn't a persisted entity until the prompt itself is saved. Renaming/deleting a tag or category globally is still Library-sidebar-only (✎/🗑 icons) — intentionally not duplicated into the Create/Edit dropdowns.
- **Never remove the unpacked extension from `chrome://extensions` to "reload" it** — Chrome deletes its entire `chrome.storage.local` LevelDB folder on uninstall with no undo, wiping all prompts/categories. Always use the ↻ reload button instead. See `[[extension-storage-data-loss]]` memory for the recovery procedure (Macrium/disk-image restore of `Local Extension Settings\<id>\`, then parse the LevelDB log's block/WriteBatch framing to recover the last-written value per key) if this happens anyway — a naive text/regex scan of the `.log` file truncates at 32KB block boundaries and misses later, larger writes.

## Deferred / future work

Additional AI providers (OpenAI/Google/local endpoint) beyond the now-live Anthropic one, cloud sync, prompt variables/templates, version/usage history, multiple libraries, bulk edit, Markdown/CSV import, command palette, site-specific insertion adapters, and an undockable/floating panel window (like Bitwarden's pop-out) are all intentionally out of scope for this release — see `Prompt Whisperer Features.md` §33 and the approved plans for details.

OpenAI and Gemini specifically cannot be added as `services/optimizer.js` providers using the same direct-`fetch`-from-side-panel pattern as Anthropic — neither API permits browser-origin CORS calls, and Google's docs warn against client-side API keys. See `Prompt Whisperer Features.md` §33 for the local-companion-process approach considered as the path forward if this is picked up.

**AI-assisted regex builder** (considered, not started): let the user describe a pattern in natural language and have the live Anthropic provider generate a regex, reusing the existing `optimizer.js` → `anthropicProvider` call pattern rather than a new provider. Validation would run client-side with JS's built-in `RegExp` (no new dependency, no Python/other-engine round-trip needed) — compile in a try/catch and test-match against a sample string before letting the user save it. Two risks to design around: (1) JS regex has no built-in catastrophic-backtracking protection, so testing AI-generated patterns should run in a Web Worker with a timeout rather than on the main thread; (2) the model can usually repair a pattern when told the concrete failing case (input string + expected vs. actual match), but fixes can regress other cases, so the UX needs a bounded multi-turn correct-and-retest loop (e.g. cap at 2-3 rounds) rather than one-shot generation or infinite retries.
